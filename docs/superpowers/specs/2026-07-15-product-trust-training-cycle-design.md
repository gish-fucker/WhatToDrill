# WhatToDrill 产品可信度与训练轮换设计

日期：2026-07-15
状态：用户已确认方向，等待书面规格复核

## 背景

用户反馈确认，当前产品已经能让新用户快速理解价值、在 30 秒内开始训练、逐组完成记录并得到下一次建议。当前最影响长期信任的不是基础流程缺失，而是产品身份和承诺不一致：页面、包名和文档使用不同名称；“下一次训练”主要复制刚完成的训练；已经上线的功能仍显示开发阶段文案；“进步”页和 Pro 结构过早暴露大量尚无当前价值的模块。

本阶段先修复这些可信度问题。组间计时、重量和次数快捷调整等训练效率工具属于后续独立阶段，避免把训练轮换、信息架构和训练执行控件同时塞进一次高风险修改。

## 目标

- 让用户在落地页、应用、PWA、法律页面、导出内容和项目文档中只看到一个一致的产品身份。
- 让“今天练什么”建立在用户的训练顺序上，而不是机械重复上一套训练。
- 让自动建议成为可解释、可确认、可修改的默认答案。
- 让“进步”页只展示当前数据能够支持的内容，并隐藏当前不可购买的商业占位。
- 保留现有疼痛安全判断、逐组记录、草稿恢复、本地优先和历史数据兼容。

## 非目标

- 不在本阶段建设云备份、多设备同步、支付或订阅购买。
- 不实现高级周期化、自动减量周、复杂动作编排或教练端计划系统。
- 不在本阶段加入休息计时器、屏幕常亮、震动、提示音或训练输入快捷按钮。
- 不把历史训练强制迁移到新的计划结构，也不伪造无法确定的训练日归属。

## 1. 统一产品身份

唯一正式名称为 **WhatToDrill**，中文副标题为 **今天练什么**，产品解释统一为：

> 根据恢复状态安排下一次训练，并逐组记录表现。

更新范围：

- 落地页品牌、标题、描述和主文案；
- 应用页品牌、浏览器标题和可访问名称；
- PWA `name`、`short_name`、图标替代文本和安装说明；
- README、`package.json`、隐私政策和使用条款；
- 周报、阶段报告、长期报告、分享内容和下载文件名；
- 服务端默认日志中的应用版本身份（不改变 API 路径）。

仓库 URL 使用当前已验证的 `WhatToDrill` 地址。GitHub 仓库简介属于外部状态，本地实现完成后单独检查；只有在当前凭据允许且不会覆盖用户设置时才更新，否则将准确交接给用户。

## 2. 最小训练轮换模型

### 2.1 用户可理解的设置

在“我的”页训练偏好中增加“训练顺序”，提供三种模式：

1. **全身循环**：始终使用同一训练日，适合每周 1–2 次或刚开始训练的用户。
2. **上下肢轮换**：上肢 → 下肢，作为每周 2–4 次用户的简单选择。
3. **自定义顺序**：从已有训练模板中选择 2–6 个训练日并排序，例如“上肢 A → 下肢 A → 上肢 B → 下肢 B”。

首次用户仍可直接开始，不增加强制注册或长问卷。默认保持“全身循环”，直到用户明确选择其他顺序；界面解释该默认项适合新手，并提供“我有固定训练顺序”入口。已有用户读取不到新设置时同样回退到全身循环，保持兼容。

### 2.2 持久化结构

在现有设置中增加兼容字段：

```js
trainingRotation: {
  mode: "full_body" | "upper_lower" | "custom",
  days: [
    { id: "rotation_day_...", templateId: "...", label: "上肢 A" }
  ],
  currentIndex: 0,
  updatedAt: "ISO"
}
```

`days` 保存模板引用和用户看到的标签，不复制整套动作。模板被重命名时显示最新模板名；模板被删除时将该训练日标记为不可用，并要求用户替换，而不是悄悄安排另一套训练。导入旧备份时字段可缺省。

训练记录补充可选的 `rotationDayId` 和 `sourceTemplateId`。只有从轮换计划开始的训练才写入，手动训练保持为空。

下一次计划升级为版本 2，并补充：

```js
{
  version: 2,
  rotationDayId: "rotation_day_..." | null,
  sourceTemplateId: "..." | null,
  rotationIndex: 1,
  sourceComparableWorkoutId: "workout_..." | null,
  userDecision: "suggested" | "changed_day" | "recovery" | "self_decided"
}
```

现有版本 1 计划在读取时规范化为全身循环建议，不丢失动作、日期或调整理由。

### 2.3 决策顺序

系统严格分两步生成建议：

1. **决定下一训练日**：根据当前轮换位置选择下一套模板。
2. **调整该训练日内容**：寻找最近一次相同 `rotationDayId` 或相同模板的训练记录，再根据完成组、实际次数、RPE 和恢复状态调整。

不再使用“刚完成的训练”作为所有负荷调整的唯一来源。若下一训练日从未完成过，直接使用模板目标并明确说明“这是该训练日的首次基线”。

安全信号拥有最高优先级：疼痛达到现有高风险阈值时，建议改为恢复训练，但不推进轮换位置；恢复较差时可减少该训练日的组数或强度。只有用户开始原建议训练日，或者在完成页明确确认“按此计划”，轮换位置才推进。仅查看、改日期或关闭对话框不推进。

## 3. 可确认、可修改的下次计划

训练完成后的结果对话框显示：

- 建议日期；
- 训练日名称；
- 动作数量和预计时长；
- 为什么轮到这套训练；
- 相比上次同套训练的主要调整。

主动作是“确认下次计划”。次级操作包括：

- 修改日期；
- 在轮换中选择其他训练日；
- 改成恢复训练；
- 选择“这次我自己决定”。

本阶段不提供任意动作级编辑，以免把完成页变成新的复杂编排器。用户选择其他训练日后，系统基于所选训练日最近一次可比较记录重新计算建议。选择“自己决定”会取消当前自动计划，但保留刚完成的训练记录。

首页优先级保持单一：

1. 有训练草稿时显示“继续训练”；
2. 否则有已确认计划时显示“开始下一次训练”；
3. 否则显示“看看今天怎么练”。

统计、支持伙伴和规律进度不与上述主动作争夺首屏视觉层级。

## 4. 文案清理与渐进展示

### 4.1 文案清理

全文检查并移除面向用户的开发阶段表述，包括“下一轮提供”“尚未实现”“未来开放”、旧产品名称和旧部署地址。已经达到 7 个有效观察日时，规律模块直接展示现有分析结果；不足时改为：

> 已获得 X 个有效观察日
>
> 有效观察日 = 当天同时记录身体状态并完成训练
>
> 下次训练前花 15 秒记录状态

技术文档可以准确说明产品边界，但用户界面不展示没有可执行下一步的内部路线图。

### 4.2 进步页解锁规则

页面按当前数据展示，而不是渲染一组空卡片：

- 0 次训练：只显示一个引导开始训练的空状态；
- 1 次训练：显示最近训练回顾和已确认的下一次计划；
- 同一动作至少 2 次：显示该动作对比；
- 至少 3 次训练：显示本周回顾和趋势；
- 至少 7 个有效观察日：显示个人训练规律；
- 覆盖 28 天且达到现有报告数据门槛：显示阶段报告。

状态评分、智能建议和最近记录只有在能提供非重复信息时才出现。具体显示判断集中到一个纯函数，避免各模块自行决定后再次堆满页面。

### 4.3 Pro 暂时退出主流程

保留现有服务端权益和长期报告实现，不删除数据结构。普通用户界面在没有真实购买入口时：

- 不渲染 Pro 长期报告卡片；
- 不显示无购买路径的套餐名或配额进度；
- 不出现“升级通道开放后”等占位文案。

已由服务器确认具有 Pro 权益的用户仍可看到并使用长期报告，避免破坏现有部署能力。账号页可显示真实的登录状态和当前可用云端建议次数，但只有当部署实际配置账号及权益服务时才出现。

## 5. 组件边界与数据流

在现有单页结构内增加小型纯函数模块，不进行无关的大规模拆分：

- `normalizeTrainingRotation`：验证并兼容训练轮换设置；
- `resolveNextRotationDay`：只决定下一训练日；
- `findComparableWorkout`：只寻找同一训练日的最近记录；
- `buildNextWorkoutPlan`：组合模板、可比较记录和恢复信号；
- `applyNextPlanDecision`：处理确认、换日、恢复和自行决定；
- `buildProgressVisibility`：根据记录数量返回进步页可见模块。

数据流：训练完成 → 保存明确完成的组 → 解析下一轮换日 → 查找同训练日历史 → 应用安全和负荷规则 → 展示建议 → 用户确认或修改 → 保存计划 → 首页读取唯一主行动。

这些函数不直接操作 DOM；渲染和事件处理只消费返回结果。这样可以用现有 Node 测试直接覆盖核心决策。

## 6. 错误处理与兼容

- 轮换设置无效、模板缺失或自定义顺序不足 2 项时，不猜测用户意图；回退全身循环并提示修复设置。
- 找不到同训练日历史时使用模板基线，不从不同训练日借用负荷。
- 用户删除当前计划所依赖的模板时，将计划标记为过期并回到今日建议。
- 导入数据先规范化轮换和计划；无法识别的新字段被忽略，旧备份仍可导入。
- 本地存储写入失败时沿用现有安全提示，不在仅保存了一半状态时推进轮换位置。
- 疼痛和恢复规则继续优先，产品不提供医疗诊断。

## 7. 测试与验证

### 自动化

- 语法检查覆盖新增模块和现有应用脚本。
- 单元测试覆盖全身循环、上下肢、自定义顺序、首次基线、同训练日比较、模板缺失、旧计划迁移、疼痛恢复覆盖和轮换推进时机。
- 冒烟测试覆盖首次用户、已有历史用户、完成后确认、换训练日、改日期、自行决定、恢复训练和首页主动作优先级。
- 进步页测试覆盖 0、1、2、3 次训练，7 个有效观察日和 28 天报告门槛。
- 品牌一致性扫描覆盖 HTML、manifest、README、法律页面、导出标题和文件名；允许历史设计文档保留旧名称作为背景证据。

### 浏览器验证

在桌面和 390px 手机视口验证：

- 落地页和应用身份一致；
- 自定义训练顺序可设置、排序和保存；
- 完成上肢后建议下肢，而负荷来自上一次下肢训练；
- 结果页的修改不会误推进轮换；
- 首页始终只有一个视觉主动作；
- 进步页不会展示无数据卡片或无购买路径的 Pro 占位；
- 页面无横向溢出，键盘焦点和对话框关闭行为正常。

## 8. 验收标准

- 面向用户的当前产品表面统一使用 `WhatToDrill · 今天练什么`，没有旧品牌或旧公开地址。
- 用户能选择全身、上下肢或 2–6 日自定义训练顺序。
- 完成一套训练后，下一建议来自轮换中的下一套，并以该套历史而非刚完成训练作为负荷依据。
- 下次计划可确认、改日期、换训练日、改恢复或取消自动决定。
- 进步页按数据量解锁，未开放商业占位不再出现在普通用户主流程。
- 现有历史、训练草稿、逐组完成、安全判断、导入导出和离线外壳继续可用。
- 自动测试通过，并完成桌面与手机浏览器实测。

## 自审

- 没有未完成标记或依赖未定义产品决策的占位项。
- 品牌、训练轮换、下次计划和进步页的目标与数据结构一致。
- 范围集中在反馈中的 P0 可信度问题以及与训练轮换不可分割的计划确认；训练中快捷工具和商业基础设施明确留到后续阶段。
- 明确了轮换何时推进、模板缺失如何处理、旧数据如何兼容，以及安全建议如何覆盖正常轮换，避免产生两种解释。
